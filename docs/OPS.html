中渔小助 · 营销自动化 Agent
运营执行层与 API 接口说明

版本 v0.5.0 ｜ 与 ZT-agent 构成「双 Agent 系统」｜ 本文档描述「从给建议到能办事，再到自己盯着干」的能力升级

一、这次升级解决了什么问题

升级前，营销 Agent 的能力边界是「看懂 + 写出」：看经营数据、写营销文案。但它发现「速攻2号已经卖断货」时，只能提示你「尽快补货」，补货这个动作仍然要你自己去收银系统里点。

升级后新增运营执行层（Action Layer），把 AI 的一句话建议变成一张可审批、可执行、可追溯的工单，覆盖四类业务动作：补库存、订单发货、退货处理、取消订单。

再进一步，新增自动运营（Autopilot）：不用人喊，系统按设定间隔自己巡检、自己干活、自己留报告 —— 对应「前期问我要不要做，后期成熟了自己运营」的完整演进。

能力升级前升级后
发现库存告急提示「建议补货」自动生成补货工单（含建议数量与成本估算），你点一下即完成补货
处理待发货订单无法感知自动生成发货工单，补录运单号后一键发货
售后处理无法感知从客户咨询里提取退换货线索，人工核实后发起退货工单
自动化程度无L0~L3 四档可调：前期每条都问你，后期成熟了自动跑
谁来触发必须人点一下可开启无人值守：定时自己巡检 → 该自动的自动执行 → 转人工的进队列 → 出报告

二、设计边界：为什么「能改数据」也不违规

一句话：营销 Agent 从不直接写业务数据库；要改数据，就请收银系统自己去改。

原来的架构承诺是「只读 ZT-agent 的业务表」。加了执行能力后，这个承诺并没有被打破，而是被细化了：

诉求做法谁保障正确性
看数据（销量 / 库存 / 订单 / 咨询）直接只读 agent_db，由 db.py 的只读引擎守卫本服务的只读守卫（任何写语句直接抛异常）
改数据（补货 / 发货 / 售后）以「后台操作员」身份调用 ZT-agent 自己已有的管理接口（HTTP + JWT）ZT-agent 自己的事务与业务规则

这样做带来三个好处：

  1. 数据一致性有保障 —— 库存扣减、订单状态机、钱包记账这些事务逻辑一份都不会被绕过，营销侧不可能写出脏数据；
  2. ZT-agent 零改动 —— 它不需要为营销 Agent 加一行代码，仍然可以独立部署、独立运行；
  3. 责任链完整 —— 这一次操作在收银系统侧同样留下日志与流水，可追溯。

三、运营执行层的四层结构

层模块职责
① 动作注册表ActionSpec / ACTION_REGISTRY声明系统能做哪些事、风险多大、需要哪些参数、是否允许自动化
② 护栏引擎decide()判定这一次该「自动执行」还是「等人点头」，并逐条记录判定理由
③ 任务状态机OperationTask待审批 → 已批准 → 已执行 / 执行失败 / 已驳回 / 已撤销
④ 审计日志ActionAudit谁、何时、依据什么、执行结果如何，全量留痕

另有执行器 zt_client.py：负责登录取 JWT、调用 ZT-agent 接口、解析响应并回写结果。

四、自主化分级（对应「前期问我，后期自己干」）

等级名称行为适用阶段
L0仅建议只生成待办，绝不执行 —— 纯参谋模式刚上线、建立信任
L1人工审批每个动作都要人工点「批准」才执行（默认）日常运营，最稳
L2限额内自动白名单动作在限额与配额内自动执行，超出自动转人工流程稳定后
L3白名单全自动白名单动作只要过护栏就自动执行成熟期

数据库写入权限（闸门）：自动执行允许改哪类数据由「数据库写入权限」控制 —— 只读（全部转人工）/ 开放库存写 / 开放库存+订单写。退货涉及资金流出，任何配置下都永远人工审批。 所有写入依然经收银系统接口执行，绝不直接碰数据库。

六、七道护栏（逐条判定，全部通过才允许自动执行）

序护栏规则
1急停开关开启后一切转人工（最高优先级）
2自主等级L0 只建议，不执行
3动作性质不可逆或涉资金 → 永久人工
4动作白名单不在名单内转人工
5等级策略L1 一律人工
6目标白名单限定试点范围（空 = 不限制）
7限额 + 每日配额超量或超次数转人工

每条判定都连同「通过 / 拦截 + 原因」一起落库，前端原样展示 —— 让「AI 为什么没敢自己动手」完全可解释，而不是一个黑箱。

七、安全机制

机制说明
幂等键只取业务标识字段（如 product_id + adjust、order_no），不含备注文本，避免「换个备注就绕过防重复」
在途去重同一动作 + 同一目标若已有「待审批 / 已批准」任务，不重复建单
重复执行拦截同一动作 + 同一目标在 10 分钟内被重复执行 → 判定误双击并拦截（时间窗设计，不阻挡合法的重复业务）
全量审计创建 / 批准 / 驳回 / 执行 / 失败 / 改策略全部留痕，可追责
演练模式dry_run 只生成「将要发起的请求」不落地，适合演练与演示
最小权限账号建议在 ZT-agent 后台为营销 Agent 单独建一个 staff 机器人账号，可随时停用，且审计日志能区分「人操作」与「Agent 操作」

八、自动运营（无人值守）：从「你喊它才动」到「它自己盯着」

第七节之前解决的都是「AI 想办事时怎么保证它不乱来」；本节解决的是「不用人喊，它自己也去办」。

开启后，服务进程内会有一个轻量调度循环，按设定间隔自动跑一轮完整闭环：

定时到点 → 巡检（库存 / 订单 / 咨询）→ 按七道护栏建单
        → 该自动的自动执行 → 转人工的进审批队列 → 留一条运行记录

人的角色随之改变：从「每天惦记着点一下巡检」变成「有空看一眼报告、处理剩下需要人拍板的那几条」。

8.1 开关与节奏

策略项默认说明
autopilot_enabledoff自动运营总开关。默认关闭，必须由人在页面上显式打开
autopilot_interval_minutes30巡检间隔，建议 30~120 分钟（数据变化没那么快，太频繁没意义）

8.2 三条安全设计

设计说明
默认关闭不与既有行为打架。升级部署后若没人去开，系统行为与以前完全一样
不新增任何权限自动运营只是「替人按下巡检按钮」。能自动执行什么完全由自主化策略与七道护栏决定——把开关打开 ≠ 放开一切，发货 / 退货 / 取消在任何情况下都不会被自动执行
绝不拖垮服务循环体整体 try/except（异常只打印不抛出，循环不退出）；数据库操作走 asyncio.to_thread 不阻塞事件循环；每 60 秒才醒一次判断是否到点

8.3 运维总闸

环境变量 AUTOPILOT_DISABLED=1（或 true / on / yes）可强制不启动调度器， 页面上的开关也随之失效。用于排障、迁移，或不希望容器后台跑定时任务的场景。

8.4 可观测性

观测点位置
是否开启 / 间隔 / 下一轮时间前端「运营任务中心」顶部状态条
每一轮干了什么前端「🤖 自动运营记录」面板（触发方式 / 巡检结果 / 新建 / 自动执行 / 转人工）
原始记录autopilot_runs 表（含本轮扫到的候选 JSON，便于复盘）
进程日志[autopilot] 调度器就绪… / 第 N 轮完成：… / 本轮异常已忽略：…

方法路径说明

十、端到端验证结果（均为真实调用实测）

用例结果
巡检生成待办✅ 扫出 3 个库存预警商品 → 生成 3 条补货待办（L1 下全部转人工）
真实补货执行✅ 批准后经收银系统接口成功补货，其侧真实库存 0 → 5，复查一致（随后原路退回，净变化为零）
真实错误处理✅ 对不存在订单发起发货 → 收银系统返回「订单不存在」，任务标记执行失败，不产生任何数据变更

幂等（在途去重）✅ 同商品同数量、仅备注不同，命中同一张在途单

审计留痕✅ 创建 / 批准 / 执行 / 失败 / 改策略全部入库可查
调度器启动✅ 启动日志出现「调度器就绪，每 60s 检查一次」
定时自动触发✅ 开启后无需任何人工操作，到点自动产生 trigger=timer 的运行记录
无人值守真实自动执行✅ L2 + 白名单商品 + 限额内 → 自动建单并自动执行，收银系统侧真实库存 0 → 100，任务标记「🤖 系统自动执行」（随后原路回滚，净变化为零）
护栏不被绕过✅ 同一轮里，白名单外的商品仍只生成待审批任务，不自动执行
急停对自动运营同样生效✅ 急停开启后跑一轮：只建单、零自动执行，目标商品库存未发生任何变化
不留测试残留✅ 验证后全部 6 个商品的库存 / 预留量 / 预警线与订单状态与验证前逐字段一致
断货自动联动（Flow A）✅ 商品库存 0 → 巡检捕获 → 自动发 pause_product → 收银系统库存接口返回 purchase_paused:true + 客户提示文案（覆盖表生效，业务表零改动）
待确认转人工✅ coord_auto_apply=off 时断货只生成待确认事件，人工点「确认下发」后才发往收银系统并生效
入站事件与白名单✅ 收到 return_requested → 登记协调事件；未知事件 → 400 拒绝
协调幂等去重✅ 同一断货商品在事件未处理前重复巡检不会重复下发
并入自动运营✅ 整轮自动运营的返回体与运行记录均含协调巡检摘要

十一、L5 多智能体编排 ——「两个 AI 助手会互相打招呼」（本轮新增）

这是整套系统的最高层能力：营销 Agent 作为协调中枢，与收银系统侧的 C 端客服 Agent 双向协同。 到此，AI 能力路线 L1 意图识别 → L2 知识检索 → L3 工具调用 → L4 多轮记忆全部补齐，进入 L5 多智能体协同与编排。

流向触发动作
营销 → 前台（Flow A）巡检发现商品断货（可用库存 ≤ 0）向客服 Agent 发 pause_product：前台暂停该商品购买，并挂出「暂时缺货，可先收藏或咨询客服」提示
营销内部（Flow B）巡检发现商品退货率飙升（≥ 阈值且样本 ≥ 3 单）生成复盘事件，提示复盘该商品的质量 / 描述 / 售后策略
前台 → 营销客服 Agent 主动发来 return_requested登记退货告知事件，供运营跟进

11.1 零侵入怎么做到的

  • 营销侧只读收银系统业务表发现信号；下发协调指令只走对方新增的接收钩子 POST /api/coordination/inbound/（staff 鉴权 + 事件白名单）；
  • 对方协调状态放在新建托管表 product_coordination（覆盖表模式），业务表一列不改、一行不迁；库存接口只读覆盖表做展示合并；
  • 每一次协调都落本服务 coordination_events 表，谁、何时、为什么、结果如何全量可溯。

11.2 开关与节奏（页面「自主化设置」可改）

策略项默认说明
coord_enabledoff跨 Agent 协调总开关，默认关闭；关掉即整体停用
coord_auto_applyoffoff=只建议（转人工确认）；on=发现即自动下发生效
coord_return_surge_threshold20退货率告警阈值（%）

L5 的三条安全底线：① 事件白名单 —— 对方只接受三种协调指令，其余一律拒绝； ② 默认转人工 —— 断货暂停虽可自动，但默认只生成建议，人点头才下发； ③ 全链路留痕 —— 每条协调事件可查「谁发现、为什么、何时下发、结果如何」，随时可整体关停。

十二、演进路线：从「每条都问你」到「成熟了自己干」

阶段配置人的角色
起步期L1 人工审批 + 演练模式先跑几轮；自动运营保持关闭逐条审批，建立对 AI 判断的信任
试点期L2 + 目标白名单（只放开 1~2 个商品）+ 小限额；自动运营开启、间隔设长一点（如 120 分钟）只在超限时才介入
成熟期L2 放宽限额，或升到 L3；自动运营间隔缩短到 30 分钟看日报、处理异常，日常不介入
任何时候急停开关 / AUTOPILOT_DISABLED=1一句话全部转人工

面试叙事建议：这套设计能同时体现五种能力 —— ① 业务理解（知道哪些动作可自动化、哪些必须人工）； ② 风险意识（幂等、限额、配额、急停、审计、演练模式）； ③ 架构功底（跨服务不改对方代码、通过既有接口与事务边界协作）； ④ 工程闭环意识（无人值守不是「放开限制」，而是默认关闭 + 复用同一套护栏 + 全程可观测可复盘）； ⑤ 多智能体编排能力（L5：协调中枢 + 事件白名单 + 覆盖表零侵入 + 默认转人工，两个 Agent 各自独立运行、按需协同）。

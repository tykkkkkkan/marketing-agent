1. 项目目标

在不改动 ZT-agent（C 端客服）核心代码的前提下，独立构建一个 B 端营销自动化 Agent：以 React 运营后台为界面、FastAPI 为后端、LangChain 编排 LLM 工作流，复用 ZT-agent 沉淀的 MySQL 数据与模型/向量基础设施，实现「销售分析 → 文案生成 → 客户分群 → 活动编排 → 合规审核」的自动化营销闭环。

2. 技术选型与理由

技术用途选型理由
React运营控制台前端组件化、生态成熟，独立于 ZT-agent 的 Vue3，展示多栈能力
FastAPIB 端后端服务异步、类型提示、自动 OpenAPI，适合 AI 工具/流式接口
LangChainAgent 编排与工具链LCEL 把多步营销工作流工程化；复用 Tool/Chain/Memory 抽象
DeepSeek (deepseek-chat)对话/生成大模型与 ZT-agent 共用同一 OpenAI 兼容接口与 API Key，降低成本与切换成本
bge-m3 + ChromaEmbedding 与向量库复用 ZT-agent 的语义检索能力做文案去重/合规/相似商品
MySQL (agent_db)共享数据底座直接只读复用 ZT-agent 已有业务表，零 ETL
Docker + nginx编排与反代与 ZT-agent 同 compose 编排，nginx 统一路由 /api/cs 与 /api/mkt

3. 系统架构

3.1 服务拓扑

  • db：MySQL 8.0，agent_db（两后端共用，营销侧只读）。
  • web：Django ZT-agent（C 端，已有）。
  • mkt：FastAPI 营销 Agent（B 端，新增）。
  • chroma：向量服务（共用 collection）。
  • nginx：反代，/api/cs→web，/api/mkt→mkt，/→React 静态。

3.2 数据流

[顾客] → [ZT-agent] 写 conversations +（命中规则）写 customer_signals → [FastAPI 营销 Agent] 定时扫 signals，读 orders/products 分析、读 knowledge_chunks+Chroma 生成文案 → 写 marketing_campaigns → [React 后台] 审核后执行。

3.3 与 ZT-agent 的关联

关联发生在数据/基础设施层（共享 agent_db、Chroma、.env 密钥、JWT 签名密钥），代码层零耦合：两个服务进程级隔离，可独立部署、独立 git 历史。

4. 关键技术方案

  • 复用 RAG/向量库：Chroma 以 server 模式暴露，两端共用 collection；营销侧用于相似商品推荐与文案合规校验。
  • LangChain Agent + Tools：定义 3 个工具——query_sales（读 orders 聚合）、read_knowledge（读知识库）、generate_copy（生成文案）；用 AgentExecutor 串联多步推理。
  • JWT 共用：FastAPI 用与 Django simplejwt 相同的 SIGNING_KEY 校验令牌，React 登录一次双端通用。
  • 事件表解耦：customer_signals 作为两 Agent 协同契约，支持重放与审计，避免硬编码互调。

5. 实施路线

阶段目标关键产出验收
P0 基础设施根 docker-compose + 共享 .env，把 db 上提到根compose 编排 db/web/mkt/chroma/nginx两服务同连 agent_db
P1 数据只读接入FastAPI 用 SQLAlchemy 只读 agent_db销量榜 / 库存预警接口真实数据一致
P2 Agent 内核LangChain Agent + 3 工具端到端生成一份营销文案能跑通工具循环
P3 运营后台React 看板 + 文案草稿 + 审核队列可演示前端闭环可用
P4 协同与事件customer_signals 联动 + 合规审核信号触发方案草稿协同闭环
P5 打磨流式输出、错误处理、文档与演示就绪可演示/面试完整可讲

6. 目录结构与部署（布局 A：兄弟项目）

中渔天下/
├── ZT-agent/                # 现有 C 端客服（独立 git 仓库，不动）
├── marketing-agent/         # 新增 B 端营销（独立 git 仓库）
│   ├── backend/             # FastAPI + LangChain
│   ├── frontend/            # React 运营控制台
│   └── docs/                # 本文档与 PRD
├── docker-compose.yml       # 根：db + web + mkt + chroma + nginx
└── .env                     # 共享：DB 凭据 / DEEPSEEK_API_KEY / JWT_SIGNING_KEY

部署：根目录 docker compose up 一键起全部服务；两个仓库各自独立提交与回滚。

7. 风险与应对

风险应对
双栈复杂度（两套后端/依赖）进程级隔离、独立 repo；面试讲清「为何分开」
数据一致性FastAPI 默认只读业务表，写只走新增表
过度承诺自动化定位「AI 辅助 + 人工审核」，MVP 不实接外部渠道
密钥泄露全部走 .env，不入库；.env.example 仅留占位

8. 面试叙事点

  • 双栈能力：「ZT-agent 自研 ReAct 验证原理，营销 Agent 用 LangChain 验证工程化，既懂底层也会用框架。」
  • 架构思维：「两个 Agent 进程级解耦、共享数据底座，用事件表协同——这是刻意的微服务设计。」
  • 业务理解：「把客服沉淀的咨询/交易数据转化为营销动作，体现从数据到业务价值的闭环思维。」
